What Is an API?

An API (Application Programming Interface) is an interface that enables communication between a client (web, mobile, desktop application, etc.) and a server.
In modern applications, the user interface (front end) simply displays data received from the API. The actual business
logic runs in the backend and API layers.

it is a structure that facilitates data exchange.

# How Do I Know If It's an API?
An endpoint does not necessarily have to include “/api” in its URL to be an API.

Example API endpoints:
/api/users
/users
/profile
/login
/graphql
/v1/profile
/customer/15
Signs that help me recognize it's an API:

• Return JSON
• Return XML
• Return data instead of HTML
• Set Content-Type to application/json
• The frontend uses this data

# HTTP Methods and the Bug Hunter's Perspective

## GET
Purpose:

To read data.
Hunter's questions:
• Can I read another user's data?
• Can the ID be changed?
• Does it return too much data?
• Is there any information disclosure?

## POST
Purpose:

To create new data or initiate a process.
Hunter's questions:
• Can I send additional parameters?
• Does the backend accept fields it doesn't require?
• Is there a business logic error?

## PUT
Purpose:

To update the entire resource.
Hunter's questions:
• Can the entire object be modified?
• Is the authorization check correct?

## PATCH
Purpose:

To update specific fields in the existing data.
Hunter's questions:
• role
• isAdmin
• verified
• credits
• balance
Can I modify fields like these?

## DELETE
Purpose:

To delete data.
Hunter's questions:
• Can I delete someone else's data?
• Has authorization been implemented correctly?

Questions I Always Ask When Reviewing an API
• Is there authentication?
• Is the authorization correct?
• What does the endpoint do?
• What is the HTTP method?
• Is there any unnecessary data in the JSON?
• Can the ID be changed?
• Can I add extra parameters?
• Is there a rate limit?
• Is there an older API version?
• Are there any hidden endpoints?
• Is the API documentation publicly available?

## Types of Open We Have Learned 

### 1. API Documentation Exposure
Key Takeaway:
API documentation is a major source of information for an attacker.
Information we can find:
• Endpoints
• HTTP Methods
• Parameters
• JSON Structures
• API Versions
Places to look in real life:

/swagger
/swagger-ui
/openapi.json
/swagger.json
/api/docs
/redoc
/api
Takeaway:
I learned how to map out an API before attacking it.

### 2. Identifying Unused API Endpoints

Lesson Learned:
The backend may still be running old endpoints even if the frontend no longer uses them.
Why does this happen in real life?
• An old mobile app
• A new frontend
• Migration
• Forgotten endpoints
From now on, I’ll keep this in mind:
“Just because the frontend isn’t displaying it doesn’t mean the endpoint has been deleted.”

### 3. Mass Assignment

Logic Learned:
The backend can automatically map all fields received from the client to the model.
Regular user:


{
“name”:“Ali”
}


Hunter:


{
“name”:“Ali”,
‘role’:“admin”,
“isAdmin”:true,
“verified”:true
}


Objective:

To test whether the backend accepts fields it doesn’t expect.
Key Lesson:
Just because I don’t see the `role` field in the response doesn’t mean I can change it.
Reading and writing are two different things.

### 4. Server-Side Parameter Pollution (Query)

Lesson Learned:
Even though I thought I was sending a single parameter, the backend might split it into separate parameters.
Example:
username=administrator%26field=email


The backend splits this into:

username=administrator
field=email


can be interpreted as follows.
Lab Takeaway:
By manipulating the request generated by the backend, I was able to read fields that I normally wouldn’t have access to, such as:
• email
• reset_token
Real-Life Lesson:
If parameters are passed on to other requests, parameter pollution can occur.

### 5. Server-Side Parameter Pollution (REST URL)
Key Takeaway:
Not only the query string, but the URL path can also be manipulated.
Logic used in the lab:
../../../../../openapi.json#
This is not a command injection.
It is more akin to:
• Path traversal
• URL path manipulation
logic.
Since the backend normalizes URLs during creation, unexpected endpoints can be accessed.
Takeaway:
I’ve now learned that URLs are also generated by the backend and can be manipulated.
